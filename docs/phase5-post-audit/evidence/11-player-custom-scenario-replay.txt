SOURCE READ (structural)
=========================
There is no dedicated "customScenario"/forced-outcome API (grepped src/, cli/ — no hits). The nearest
match is Studio's Play tab "Find any win"/"Find symbol win": a real, repeated, authoritative spin-and-check
search, not a forced outcome — cli/studio/runtime/StudioPlayService.ts:312-347 (findAnyWin/findSymbolWin),
:368-398 (spinUntilMatch), bounded by maxFindScenarioSpins (default 2000, line 132); on exhaustion it
returns an explicit {status: "error", error: "No matching round was found within N spins."} rather than
silently returning a non-matching round — asserted by existing real tests
tests/cli/studio/runtime/StudioPlayService.test.ts:466-491,597-610.

Replay determinism model: `pokie replay` / Studio Replay never replays recorded RNG values — it re-plays a
fresh session forward from round 1 using the same seed. Explicit, not hidden:
  - src/replay/ReplayRecorder.ts:11-13: "There is no seek-to-round primitive... Reproducibility for a given
    seed depends entirely on the game package actually threading context.seed into a deterministic setup."
  - cli/commands/ReplayCommand.ts:76: CLI's own description: "Best-effort replay of a single round..."
  - cli/studio/replay/StudioReplayExecutionService.ts:51-57,229-236: same best-effort, chunked
    forward-replay, same caveat repeated.
  - cli/studio-client/src/domain/interpret/Replay.ts:344-364,412-493: comparison/gating logic is
    capability-aware — only calls a reproduction "ready"/verified when an original debug.reelStops trace
    exists; otherwise labels it "bestEffort" (line 487): "Reproduce is still offered, but only as a
    best-effort forward replay: it is explicitly non-verifiable, never presented as an exact match."

Root cause of the (now-fixed) determinism gap this concern's framing hypothesizes: reel-stop *position*
draws and reel-strip *content* shuffling are two separate RNG consumers.
src/session/videoslot/combinations/PseudorandomNumberGenerator.ts:5 (SymbolsCombinationsGenerator) and
src/session/videoslot/combinations/SymbolsSequence.ts:122-132 (shuffle()) both default to unseeded
Math.random() unless a caller injects a seeded RNG. Before commit 582f532, generated packages seeded only
the first (stop-position draws) and left the second (reel-strip content shuffle) unseeded, so a supplied
seed controlled *where* reels stopped but not *what symbols* sat there — a silent, non-obvious replay
mismatch. Fixed by [P5-POLISH-19] commit 582f5323efdd1baaa6c95bb00f761def24b2c287 ("make generated-package
rounds seed-reproducible, prove four-surface parity", 2026-08-08), threading context.seed into both, across
every codegen template (src/generated/renderBuiltGameModule.ts, cli/scaffold/renderEntryModule.ts,
renderGameModule.ts, renderSessionModule.ts — see `git show 582f532` for the diff).

CLASSIFICATION: FALSE POSITIVE (fixed)
=========================================
The determinism defect class this concern's own framing hypothesizes ("does a custom scenario/seed force
the claimed outcome reliably, or can it silently fall through to normal RNG") was a real, confirmed bug in
this codebase for generated packages — already found and fixed under P5-POLISH-19
(582f5323efdd1baaa6c95bb00f761def24b2c287, 2026-08-08). This round independently re-verified the fix holds
at current HEAD (0494a77) by generating a fresh package through the real GamePackageGenerator codegen path
and replaying it twice — bit-for-bit identical (screen (c) above). The residual, narrower risk — hand-
authored/bespoke sessions that don't fully seed every RNG consumption point — is real and reproducible
(screen (b) above) but is a pre-acknowledged, explicitly documented design boundary ("best-effort replay",
never presented as an exact match unless a debug.reelStops trace exists to verify against), not a hidden
defect; it does not change this entry's classification since it is a distinct, already-disclosed limitation
rather than the silent-fallthrough failure mode being audited.
