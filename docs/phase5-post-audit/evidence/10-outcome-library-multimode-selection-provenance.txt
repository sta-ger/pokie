SOURCE READ (structural)
=========================
Selection is filename-exact, not fuzzy. OutcomeLibraryBundleReader.readModeIndex
(src/weightedoutcome/bundle/OutcomeLibraryBundleReader.ts:37-40) and
OutcomeLibraryBundleOutcomeSource.drawOutcome
(src/weightedoutcome/bundle/OutcomeLibraryBundleOutcomeSource.ts:32-53 — the class actually wired into
`pokie serve`/Studio Play/Simulation/Replay: src/project/simulateOutcomeSourceProject.ts:49,
cli/studio/runtime/StudioPlayService.ts:440, cli/studio/simulation/StudioSimulationService.ts:355,
cli/studio/replay/StudioReplayExecutionService.ts:398) both open `index_${modeName}.json` by exact string
interpolation of the caller-supplied mode name — no case-folding, no partial match, no "closest mode"
fallback.

    public async readModeIndex(bundleDir: string, modeName: string): Promise<OutcomeLibraryBundleModeIndex> {
        const raw = await fs.promises.readFile(path.join(bundleDir, `index_${modeName}.json`), "utf-8");
        return JSON.parse(raw) as OutcomeLibraryBundleModeIndex;
    }

Write-time invariants prevent POKIE's own writer from ever producing a mode/content mismatch:
OutcomeLibraryBundleWriter (src/weightedoutcome/bundle/OutcomeLibraryBundleWriter.ts) writes
index_<modeName>.json with modeName derived from the same value used for the filename (lines 142/160-171),
and enforces cross-mode provenance homogeneity (every mode in one bundle must share game id/version/
configHash/pokieVersion, lines 120-139; error code
outcome-library-bundle-cross-mode-provenance-mismatch otherwise).

Deployment layer rejects a selector whose own mode name doesn't match its deployment row before ever
loading it — cli/studio/deployment/StudioDeploymentService.ts:51-62,131-161
(describeSelectorModeMismatch).

Provenance is never recomputed on a second path. OutcomeLibraryBundleManifestModeEntry.generator
(src/weightedoutcome/bundle/OutcomeLibraryBundleManifest.ts:20-25) is copied verbatim from
generateExactWeightedOutcomeLibrary's own diagnostics and is present only for modes actually generated by
POKIE (absent for hand-authored/JSONL-sourced modes); this distinction survives into Studio's
StudioOutcomeLibraryRegistryView (cli/studio/outcomeLibrary/StudioOutcomeLibraryRegistryView.ts:20-24) and
is per-mode, per-source-bundleDir accurate (StudioOutcomeLibraryGenerateService.registry(),
cli/studio/outcomeLibrary/StudioOutcomeLibraryGenerateService.ts:294-343).

Documented trust boundary: OutcomeLibraryBundleReader's own class doc (lines 26-30):

    // Reads a canonical outcome-library bundle back — see OutcomeLibraryBundleWriter for what it wrote.
    // Assumes an already-valid bundle (see OutcomeLibraryBundleValidator for a bundle from an untrusted
    // source) and throws (OutcomeLibraryBundleInvariantError, or whatever a malformed read naturally
    // throws — a missing file, invalid JSON) rather than returning ValidationIssue[] — the same "assume
    // already validated, fail fast on a genuine surprise" contract WeightedOutcomeSelector has toward
    // WeightedOutcomeLibrary.

Consistent with that doc comment, neither `pokie serve` (cli/commands/ServeCommand.ts) nor
StudioPlayService.ts runs OutcomeLibraryBundleValidator before wiring a bundle directory into live spin
serving — only `pokie outcomelibrary validate`, OutcomeSourceProjectAnalyzer, and
CertificationEvidenceBundleVerifier/StudioCertificationService do so, as an explicit opt-in step. The
specific check that would catch a bundle whose index_<modeName>.json's own internal modeName field
disagrees with its filename (outcome-library-bundle-mode-index-mode-name-mismatch,
src/weightedoutcome/bundle/OutcomeLibraryBundleValidator.ts:413-420) is therefore not automatically
enforced before a spin is served; readAndVerifyOutcomeAtByteRange
(src/weightedoutcome/bundle/internal/readOutcomeAtByteRange.ts:55-94) verifies id/weight/recordHash per
draw (catching content tampering) but never cross-checks index.modeName against the requested mode name.
This can only diverge from a bundle POKIE's own writer produced through external tampering/corruption —
exactly the "untrusted source" scenario the docs already assign to OutcomeLibraryBundleValidator, not the
reader.

CLASSIFICATION: INTENTIONAL SUPPORTED LIMITATION
===================================================
No genuine, currently-reproducible defect in multi-mode selection or provenance reporting was found.
Selection is exact-match and fails loudly rather than silently substituting another mode's data, and
provenance is threaded verbatim (never recomputed on a second path) through every layer traced. The one
narrow trust boundary — runtime read/serve trusts an already-valid bundle, with a separate opt-in validator
covering a mode's own internal self-consistency against an untrusted source — is explicit in
OutcomeLibraryBundleReader's own class doc, matching a deliberate design choice rather than an oversight.
