# POKIE v1.3 — Closeout Report

Date: 2026-07-26. This closes out `GAP_AUDIT_v1.3.md` (added 2026-07-19 at `develop` HEAD `10716a7`, since
deleted — see below), which code-audited every subsystem against the v1.3 product roadmap and produced a
10-item priority list plus a shortlist of lower-priority infrastructure gaps. All 10 priority items, and the
infrastructure gaps that were in scope for v1.3, are now resolved. This report is the permanent record of that
list and its resolution, replacing the now-superseded audit file itself.

## Priority list — all resolved

1. **PAR sheet: stop silently dropping `winModel`/`mechanics`/`betModes`.** Resolved — round-trip mapping added
   for all three (see [PAR sheet round-trip](cli.md#workbook-format) and `dfae3f3`).
2. **Bet-mode as a first-class, opt-in runtime hook** (ante-bet stake modifier, buy-bonus forced entry).
   Resolved — `BetMode.runtimeType`, `VideoSlotWithBetModesSession`, `ForcedFeatureEntryHandling` (see
   [Bet Modes](README.md#contents), item 8).
3. **Per-bet-mode statistics in live `Simulation`/`pokie sim`.** Resolved — `pokie sim --mode`, per-mode target
   RTP comparison/diff reporting (`3be99a1`, `e2b8090`).
4. **Studio surface for Certification/Evidence Bundle and Provably Fair.** Resolved —
   `CertificationTab.tsx`, `ProvablyFairTab.tsx` in `cli/studio-client/src/components/project/`.
5. **Studio surface for `pokie stakeengine export`.** Resolved — `StakeEngineExportTab.tsx`.
6. **Convergence/adaptive early-stop for Simulation.** Resolved — `SimulationConvergenceChecker`,
   `ParallelSimulationRunOptions.convergence`, `pokie sim --rtp-tolerance` (`f310da5`).
7. **Stake Engine vs. External Adapter SDK architectural fork.** Resolved by explicit decision, documented
   rather than unified: Stake Engine's export format is static/batch, not a live `ExternalDeploymentTarget`
   session — implementing it as one would misrepresent the SDK's live-delivery contract. The rationale is
   recorded in [`external-adapter-sdk.md`](external-adapter-sdk.md) and [`stake-engine-export.md`](stake-engine-export.md)
   (`6e3381c`).
8. **Reconciliation/retry palliative for non-atomic spin sequencing.** Resolved for v1.3 — `SpinOperationCheckpoint`,
   `SpinReconciliationService`, wired into `SpinCommandHandler` (`90d0502`). True cross-store atomicity remains
   a v2 concern; see below.
9. **Hold & Win and/or Jackpot as concrete decorator classes.** Resolved — `VideoSlotWithHoldAndWinSession`
   (`d3be679`), `VideoSlotWithJackpotSession` (`9a8578c`).
10. **`pokie fairness commit`/`reveal` CLI subcommands.** Resolved — `pokie fairness seed-commit`/`commit`/
    `reveal`/`verify` (`379e9cf`), input handling hardened in `7b4a2c6`.

## Below-priority infrastructure gaps — resolved

## Deferred to v2.0

Two items from the original audit remain out of scope for v1.3 and are recorded here rather than left to drift:

- **True cross-store atomicity in `SpinCommandHandler`.** The wallet, `SessionRepository`, and
  `IdempotencyRepository` are independently pluggable storages by design; making a debit→play→credit→save
  sequence a real database transaction across all three would require mandating a single shared transactional
  store, which breaks that composition model. v1.3 ships the honest boundary (documented in
  `SpinCommandHandler`'s own class comment and [`cli.md`](cli.md#failure-handling-is-best-effort-compensation-not-a-transaction))
  plus a reconciliation/retry palliative (item 8 above) that closes the dangerous case — an unrecoverable
  partial write — without claiming full atomicity. A v2 that wants real atomicity needs an architectural
  decision on a mandated transactional store first.
- **Docs site / interactive playground.** `docs/` remains a flat set of Markdown files with no generated site
  or in-browser sandbox (CodeSandbox/StackBlitz-style). This is a net-new tooling investment (site generator,
  hosting, playground runtime) rather than a gap in the library itself, and is left for a dedicated v2
  initiative.

Not tracked as a v2 engineering item: the audit's "FromStan org/npm migration" note is a brand/publishing
decision (npm scope, GitHub org), not a code gap — `package.json`, `README.md`, and the git remote are already
internally consistent on the current name and require no v1.3 or v2 code change either way.
